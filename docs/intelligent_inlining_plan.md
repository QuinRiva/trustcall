# Detailed Technical Plan: Intelligent Schema Inlining

This document outlines the plan to implement a sophisticated "intelligent inlining" feature for the `gemini_ref_strategy="intelligent"` option in `trustcall`.

#### 1. Core Objective

The goal is to modify the schema generation process so that it only inlines a referenced definition (`$ref`) if that definition is used **exactly once** throughout the entire schema. This will produce the most compact and readable schema possible by:
*   **Inlining single-use definitions:** Eliminates the need for a `$defs` entry, reducing overall schema size.
*   **Preserving multi-use definitions:** Avoids massive schema bloat by defining an object once and referencing it multiple times.
*   **Handling recursion:** Implicitly avoids infinite loops, as a recursive definition is, by nature, used more than once.

#### 2. The Two-Pass Algorithm

The implementation will be a two-pass algorithm that operates on the JSON schema generated by Pydantic.

**Pass 1: Reference Counting**

A new function, `_count_references(schema: dict) -> dict[str, int]`, will be created.
*   **Input:** The full JSON schema dictionary.
*   **Logic:**
    *   It will initialize an empty dictionary, `ref_counts`.
    *   It will define a nested recursive function, `_walk(node)`, that traverses every dictionary and list within the schema.
    *   When `_walk` encounters a key `"$ref"`, it will parse the definition name from the path (e.g., `#/defs/Address` -> `Address`).
    *   It will then increment the count for that definition name in the `ref_counts` dictionary.
*   **Output:** A dictionary mapping each definition name to its usage count (e.g., `{'Address': 20, 'UseCaseField': 1}`).

**Pass 2: Selective Inlining Transformation**

A new function, `_selective_inline_transform(node: Any, all_defs: dict, ref_counts: dict, inlining_path: set) -> Any`, will be created to perform the selective inlining.
*   **Input:** It will accept the `ref_counts` dictionary from Pass 1 and an `inlining_path` set to track the current recursion stack.
*   **Core Logic:**
    1.  When the function encounters a `$ref` to a definition (e.g., `DefA`):
    2.  It first checks the `inlining_path`. If `DefA` is already in the path, it's a recursive call. It immediately returns the `$ref` pointer to prevent an infinite loop.
    3.  If not recursive, it checks the `ref_counts` dictionary for `DefA`.
    4.  **If `ref_counts['DefA'] == 1`:** It will proceed with inlining. It adds `DefA` to the `inlining_path`, recursively calls itself on the definition from `all_defs`, and returns the fully transformed (inlined) result.
    5.  **If `ref_counts['DefA'] > 1`:** It will **not** inline. It returns the `$ref` pointer as is, knowing it will be more efficient to keep it as a reference.

#### 3. Integration with `trustcall`

This new two-pass algorithm will be integrated seamlessly into the existing `intelligent` strategy.

*   The `_get_schema` function in `trustcall/schema.py` will be the entry point.
*   When `gemini_ref_strategy` is `"intelligent"`, it will first call `_count_references`.
*   It will then call the new `_selective_inline_transform` function, passing the schema and the reference counts.
*   The resulting selectively-inlined schema will then be passed to the existing `_make_schema_gapic_compatible` function in `trustcall/utils.py`, which will handle the final, necessary transformations (renaming `_ref`/`_defs`, uppercasing types) before it's sent to the API.

#### 4. Potential Interactions & Edge Cases

*   **Interaction with `_make_schema_gapic_compatible`**: This plan ensures a clean separation of concerns. The new logic handles the *inlining strategy*, while the existing `_make_schema_gapic_compatible` function handles the final *syntactical transformation* for the Google API. This is a robust design.
*   **Nested References**: The reference counting in Pass 1 is comprehensive. It will walk the entire schema, including definitions within `$defs`, so it will correctly count all nested and transitive references.
*   **Performance**: For very large schemas, the two-pass approach introduces a small amount of overhead. However, this is negligible compared to the network latency of the LLM call and is a worthwhile trade-off for the significant reduction in schema size and improved readability.
